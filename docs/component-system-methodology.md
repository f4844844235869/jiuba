# 基于 shadcn 的组件体系演进方法

本文档用于沉淀当前项目在 `shadcn` 基础上做二次开发的思考框架。目标不是一次性定义完整组件库，而是提供一套可渐进推进、可持续收敛的演进方法。

适用范围：

- `packages/ui` 中的基础组件、复合组件、业务组件
- `apps/web` 中对共享组件的消费方式
- 后续组件抽象、命名、迁移、收敛时的判断依据

## 1. 为什么需要“体系”

如果只把组件理解成一堆零散控件，通常会出现这些问题：

- 同一种交互在不同页面各写一套
- 同名组件职责越来越混乱
- 样式、交互、状态处理不一致
- 后续想统一改造时成本很高

这里说的“体系”，本质上是在回答三个问题：

- 某个能力应该放在哪一层
- 某个组件应该负责到什么边界
- 某个抽象应该在什么时候发生

体系不是为了追求抽象完整，而是为了让后续每次新增和重构都有一致判断标准。

## 2. 当前项目的推荐分层

结合当前 monorepo 结构，建议将组件能力分为三层。

### 2.1 原子层

目录：

- `packages/ui/src/components`

定位：

- 最底层的通用设计原语
- 负责统一样式、尺寸、状态、基础交互
- 不直接表达具体业务语义

典型组件：

- `Button`
- `Input`
- `Textarea`
- `Select`
- `Dialog`
- `Checkbox`
- `Tabs`

判断标准：

- 如果这个组件脱离任何业务页面仍然成立，它大概率属于原子层
- 如果它解决的是“输入框怎么表现”“按钮怎么反馈”“弹窗怎么打开关闭”，它大概率属于原子层

### 2.2 复合层

目录：

- `packages/ui/src/components/primitives`

定位：

- 由多个原子组件组合成一个明确语义的通用控件
- 对高频交互做标准化封装
- 带场景语义，但不绑定具体业务域

典型组件：

- `InputGroup`
- `SearchInput`
- `AsyncSelect`
- `FilterInput`
- `TableToolbar`

判断标准：

- 如果它底层依赖多个原子组件组合
- 如果它解决的是一类高频交互而不是某个业务领域
- 如果多个页面都会重复手写这类拼装逻辑

### 2.3 业务层

目录：

- `packages/ui/src/components/business`

定位：

- 面向具体业务场景的可复用积木
- 负责业务展示骨架、复杂领域交互、结构化页面片段

典型组件：

- `AdminLayout`

判断标准：

- 如果它已经明显表达业务对象或业务流程
- 如果它本身就是一块页面级积木
- 如果它的 props 已经开始围绕业务模型设计

### 2.4 页面层

目录：

- `apps/web/app`

定位：

- 页面逻辑、数据获取、模块编排
- 不承担共享组件库的沉淀职责

说明：

- 页面层可以先出现临时实现
- 但当某种实现开始跨页面重复时，应回收至 `packages/ui`

## 3. shadcn 在这个体系里的角色

`shadcn` 在本项目中更适合扮演“基础生成器”和“底层参考实现”，而不是最终组件库本身。

建议理解为：

- `shadcn` 负责提供基础起点
- `packages/ui` 负责形成团队自己的稳定 API
- `apps/web` 负责消费，而不是重新发明一套

这意味着后续工作的重点不是“继续加更多 shadcn 原件”，而是：

- 哪些基础组件要做团队化增强
- 哪些高频交互要升级成复合组件
- 哪些业务片段值得沉淀成共享业务组件

## 4. 渐进式演进原则

不应该试图在一开始就设计完整体系。更合理的方法是边用边收敛。

### 4.1 先盯高频重复问题，不做全盘设计

优先识别这些情况：

- 同类 UI 在 3 个以上页面重复出现
- 每次都要重新拼图标、按钮、校验、状态
- 不同页面行为接近，但实现不一致

常见起点通常是：

- 输入
- 搜索
- 选择
- 弹窗
- 表格工具栏

### 4.2 先抽最小可复用语义，不追求大而全

例如不要一开始就做完整表单引擎，可以先只做：

- `SearchInput`
- `AsyncSelect`
- `TableToolbar`

每个组件只先解决一组明确问题，例如 `SearchInput` 第一版只做：

- 搜索图标
- 清空按钮
- 回车触发
- `loading` 状态
- `onSearch` 事件

### 4.3 采用“使用中抽象”，不要“预设式抽象”

建议遵循下面的节奏：

- 第一次出现：正常实现
- 第二次出现：比较共性和差异
- 第三次出现：正式抽象

这样抽出来的组件更贴近真实场景，不容易出现抽象过度。

### 4.4 每次抽象都要固定归属层级

新增一个组件时，必须先判断它属于哪一层：

- 原子层
- 复合层
- 业务层
- 页面层

只要归属不清，后续职责就容易继续膨胀。

## 5. 一个简单的判断模型

新增或重构组件时，可以依次问下面几个问题：

1. 它是否脱离业务上下文也成立？
2. 它是在解决单个控件问题，还是一类交互问题？
3. 它的 props 是通用 UI 属性，还是业务模型属性？
4. 它是否已经在多个页面重复出现？
5. 它是否值得被团队统一维护？

可以用下面的速判方式：

- 只负责基础样式和状态：原子层
- 组合多个原子并表达一类高频交互：复合层
- 直接表达业务对象或业务流程：业务层
- 只在单页面成立且没有复用证据：先放页面层

## 6. 推荐的渐进式推进方式

建议按主题逐步推进，而不是横向铺满整个组件库。

### 6.1 第一阶段：输入体系

目标：

- 收敛所有文本输入相关交互

建议步骤：

1. 保持 `Input` 只负责基础输入能力
2. 继续把 `InputGroup` 作为输入复合容器
3. 新增 `SearchInput`
4. 在 1 到 2 个页面试点替换
5. 根据替换结果回调 `Input` 和 `SearchInput` API

适合沉淀的能力：

- 前后缀
- 清空按钮
- 回车提交
- 搜索图标
- 加载状态
- 错误态

### 6.2 第二阶段：选择体系

目标：

- 收敛所有“单选、多选、远程搜索选择”交互

建议关注：

- `Select`
- `Command`
- `Popover`
- 未来的 `AsyncSelect` 或 `EntityPicker`

### 6.3 第三阶段：容器与操作体系

目标：

- 收敛工具栏、筛选栏、弹窗表单、表格操作区

可能产出：

- `TableToolbar`
- `FilterBar`
- `FormDialog`

### 6.4 第四阶段：业务积木体系

目标：

- 将已稳定的页面片段抽成可复用业务组件

适用前提：

- 已经有稳定的原子层和复合层支撑
- 至少有两个场景可复用

## 7. 迁移策略

组件体系的形成，不只是“新增组件”，还包括“回收临时实现”。

建议采用小步迁移：

1. 先在页面层完成真实需求
2. 发现重复后，在 `packages/ui` 中抽象
3. 选择 1 到 2 个页面替换验证
4. API 稳定后再推广到更多页面

不建议：

- 一次性全局替换
- 在没有真实场景验证前就冻结 API
- 在 `apps/web` 和 `packages/ui` 同时维护同名组件源头

## 8. 当前仓库的具体约束

基于当前项目结构，建议遵循以下约束：

- `packages/ui/src/components` 是基础原子组件的主要沉淀位置
- `packages/ui/src/components/primitives` 是增强原子和复合组件的正式承接位置
- `packages/ui/src/components/business` 是共享业务组件的沉淀位置
- `apps/web/app` 是页面和模块逻辑的实现位置
- `apps/web/components` 不应长期维护与 `packages/ui` 平行分叉的共享组件副本，除非明确是应用私有定制

当前已经落地的首个 `primitives` 组件是 `SearchInput`。它代表的不是某个业务组件，而是对“搜索输入”这类高频交互模式的统一承接方式。

如果未来通过本地 registry 分发业务组件，也应尽量保证“源头唯一”，避免共享源文件和安装副本长期分叉。

## 9. 这套方法的最终目标

这套方法不是为了把组件库做大，而是为了做到：

- 新需求出现时知道先放哪一层
- 重复实现出现时知道何时抽象
- API 演进时知道该由哪一层承担变化
- 团队新增组件时能遵循一致判断标准

简化成一句话：

不是先想清楚全部，再开始做；而是在真实使用中持续回收、分层、标准化，逐步把组件库做成体系。
